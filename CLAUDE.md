# Charging park electricity cost model

## Goal
Estimate the annual electricity procurement cost of a DC HPC charging park from
session data that has NO metered energy. Energy per session is modeled from
sampled vehicle type, arrival SOC and SOC-dependent charging curves, limited by
plug-in duration and by the site grid connection (load management).

## Layout
- Package `src/chargepark/`: `config` (load + validate config.yaml), `io`
  (sessions, prices, synthetic prices), `curves` (charging-curve databanks),
  `representatives` (k-medoids reduction), `vehicles` (catalog + sampling),
  `simulate` (numba core + load management), `procurement`, `montecarlo`
  (run loop, k comparison), `report` (summary + plots), `cli`.
- CLI: `python -m chargepark run|curves|compare-k ...` (see `cli.py` docstring).
- Tests: `pytest` in `tests/`. Tests on real data skip if the files are absent.
- `reference/charging_park_cost.py` is the original prototype (not used).

## Input data
- `data/sessions_*.csv`: columns `date` (YYYY-MM-DD), `arrival_time` (HH:MM),
  `end_time` (HH:MM). One row per session, one calendar year.
  - `end_time <= arrival_time` means the session ends on the next day.
  - Duration is PLUG-IN time, not charging time. Drivers leave at end_time
    regardless of how much energy they received.
  - Sessions running past 31 Dec are truncated at year end (accepted).
  - Invalid rows are dropped and reported with a reason.
- `data/prices/DA_{year}_15min_Germany_SMARD.nc`: SMARD day-ahead prices,
  Germany, EUR/MWh, 15 min, variable `EUR per MWh`, coordinate `time`, German
  local time (DST gap in March; the repeated October hour is averaged).
  2025 is complete; 2026 ends 2026-10-27 (a 2026 run fails the gap check).
- No ID prices are available. `prices.id.path` is null and procurement runs in
  `da_only` mode. The loader supports per-series files (NetCDF or CSV), per-series
  timezone (`local`, `UTC+01:00`, IANA) and checks DA/ID alignment when both exist.
- `data/ev_curves/fastned/` (PRIMARY): DC charging-curve databank extracted from
  `ev_charging_curves_databank.zip`; see its README.md. Used files:
  `out/curves_wide.csv` (kW at SOC 0..100 %) and `out/vehicles_databank.csv`.
  Filters: `has_curve == 1`, `battery_kwh_from_name` not null, category in
  `curves.fastned.categories` (default CAR), one curve per `curve_group_id`
  (the version with battery closest to the group median). Result: 133 curves.
  Cite Fastned as the source; check their terms before client use.
- `data/ev_curves/evkx/` (OPTIONAL, off by default, `curves.evkx.enabled`): not
  present yet. The loader assumes a vehicles file + wide curve file with column
  names in `curves.evkx.columns`; verify against the evkx README when the data
  arrives. Filters: `curve_quality == "ok"`, estimated dropped unless
  `include_estimated`, peak_kw <= `max_peak_kw` (600), capacity =
  `usable_kwh_0_100`. Fastned wins when brand/model exists in both.
- `data/processed/`: representatives outputs (`representatives_k{k}*.csv`,
  cluster plots, `elbow.csv/png`), generated by `python -m chargepark curves`.

## Model spec
1. Vehicle catalog = representative real curves with weights. Curves are capped
   at `site.charger_kw` and clustered by weighted k-medoids (PAM, numpy) on
   capped kW at SOC 0, 5, ..., 100 plus `battery_kwh x battery_weight`.
   `representatives.k` is an int or `"all"`; default `"all"` (see below).
   Member weight 1 per curve by default; `representatives.weights_csv`
   (brand, model, weight) is the hook for registration-based weights.
2. Per Monte Carlo run, sample per session: a catalog entry (by weight) and
   arrival SOC ~ Beta(a, b). Target SOC 0.80.
3. Simulate at 1-min resolution. Curve power is linearly interpolated between
   integer SOC points. Requested DC power =
   min(charger kW, curve(SOC) x derating(month), power to reach target).
4. Power convention (assumption): curve values are DC power at the connector.
   Grid draw = P_dc / `site.charger_efficiency` (0.95). SOC gain =
   P_dc x `vehicles.vehicle_efficiency` (1.0) x dt / battery_kwh.
5. Load management on grid power: if the sum of requests exceeds the grid cap,
   allocate by `equal_share` (water-filling, default), `proportional` or `fifo`.
6. Also simulate without the cap, to report energy lost to the cap.
7. Aggregate to 15 min. Procurement: PPA share at fixed price, then
   `da_only` (rest at DA, perfect forecast, no balancing cost; default),
   `forecast` (DA buys the in-sample average profile, ID settles the
   deviation; needs ID) or `fixed_split` (needs ID).
8. Report P10/P50/P90 over runs: energy, energy lost, curtailed sessions,
   binding hours, peak 15-min load, total cost, EUR/MWh.

## Choice of k (2025-11-10)
`compare-k` on `sessions_dummy.csv` with 2025 DA prices, 50 runs each:
every k in {3, 5, 8, 12} overestimates annual energy vs. k = "all" by +1.7 to
+3.6 % (EUR/MWh within 0.07). The bias does not fall steadily with k and stays
below 1 % only from about k = 30, because medoids skew towards larger
batteries and higher mid-SOC power. Runtime does not depend on k, so cost runs
use k = "all". Small k are for communication (cluster plots), not for costing.

## Assumptions (keep configurable, never present as real data)
- Chargers: 150 kW DC each. Grid cap: 500 kW (about 1/3 to 1/2 of installed power).
- Arrival SOC distribution, PPA share and PPA price: placeholders.
- Vehicle mix: equal weight per distinct curve, NOT market shares, until a
  weights CSV is provided.
- Fastned curves reflect about 30 C battery conditions. Optional
  `vehicles.temperature_derating` (12 monthly factors on curve power), off by
  default.
- `charger_class` is kept in the curve data but not used yet.

## Conventions
- Python, numpy/pandas; the minute loop is compiled with numba (`@njit`).
  Never loop over minutes in plain Python.
- All parameters in config.yaml, nothing hardcoded in the logic. Relative paths
  in the config resolve against the config file's folder.
- Cost scope is energy procurement only (no grid fees, levies, taxes).
- Plots: colors #005B4C (green), #0000FF (blue), #00002C (navy),
  #6544FE (purple), #FF7F69 (pink); always a legend when there are 2+ series.
- No em dashes in any generated text or labels.
- Never present placeholder assumptions or synthetic prices as real data.
